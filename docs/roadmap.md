# 남은 개발 계획

원 계획서(`generic-shimmying-rabin.md`)는 W8 까지의 기능 채우기를 다룬다.
기획서의 9개 기능은 사실상 모두 구현되었으므로, 이 문서는 **무엇을 더 만들지**가
아니라 **무엇이 이 서비스의 축인지**에서 출발해 남은 작업을 정리한다.

---

## 이 서비스의 축

> **남이 하는 말이 나에게 얼마인지 계산해서,
> 대부분의 경우 "그건 당신에게 중요하지 않습니다"라고 정직하게 말하는 것.**

만든 기능들은 개별 항목이 아니라 전부 같은 축의 사례다:

| 입력 | 세상이 하는 말 | 이 서비스가 하는 말 |
|---|---|---|
| 사기 문자 | "제도 바뀌니 지금 갈아타세요" | 연 **9만 9,000원**이 상한입니다. 갈아탈 이유가 안 됩니다 |
| 뉴스 | "ISA 세제 개편" | **발표(1/5단계)**입니다. 고객님껜 연 **2만 6,706원** |
| 진단 결과 | "69세 고갈" | 월 **113만원** 줄이면 95세까지 갑니다 |
| 안정도 점수 | "98점 양호" | 여유는 **월 5만원**뿐입니다 |

넷 다 "모호하거나 과장된 말 → 내 자산 기준 금액" 환산이다. 뒤의 둘은 **우리 자신의
출력**마저 같은 방식으로 환산한 것이다.

### 왜 이것이 차별점인가

"당신에겐 영향 없습니다"라고 말할 인센티브가 있는 주체가 시장에 없다. 금융사는
상품을 팔아야 하고, 뉴스는 클릭이 필요하고, 챗봇은 그럴듯한 답을 해야 한다.
은퇴계산기는 많지만 "이 뉴스는 당신과 무관합니다"를 계산해주는 것은 없다.

시니어 금융 피해의 본질이 "그럴듯한 말에 넘어가는 것"이라는 점과 정확히 맞물린다.

### 캐시플로우 엔진은 심장이지 정체성이 아니다

원 계획서도 같은 말을 한다 — "④도 ⑦도 ⑨도 '내 자산에 얼마 영향'을 계산할 수
있어야 차별화되는데, 그 계산이 곧 이 엔진이다." 엔진은 위 표의 **오른쪽 열을
가능하게 하는 수단**이다. 엔진만 자랑하면 "정교한 은퇴계산기"가 되고 그것은
차별화가 아니다. `verify_numbers` 도 마찬가지로, 오른쪽 열을 **믿을 수 있게**
만드는 장치다.

## 목표 상태 — 런타임 워크플로우

```
사용자 입력
    ↓
Supervisor (규칙 우선, 애매할 때만 LLM)          [있음]
    ├─ profiling    → 슬롯 추출 → UserProfile     [있음]
    ├─ fraud_check  → 규칙 + 팩트시트 → 환산      [있음]
    ├─ what-if      → ★ 에이전트 루프             [없음 ← 남은 일의 대부분]
    └─ other
                          ↓
              ┌───────────────────────┐
              │  도구를 쥔 에이전트     │
              │  LLM은 인자만 고른다    │
              └───────────────────────┘
                          ↓ 반복 호출
    simulate_plan / prescribe / policy_impact / check_message / sensitivity
                          ↓
              core/ 엔진 (숫자는 여기서만 나온다)  [있음]
                          ↓
              verify_numbers + trace 표시          [절반]
```

엔진과 도구 재료는 이미 다 있다. **없는 것은 루프 하나다.**

---

## A. 대화형 에이전트 — 남은 작업의 대부분

지금 LLM 이 불리는 곳은 세 군데뿐이고 전부 단발(one-shot)이다. 도구 호출도,
루프도, 자율 계획도 없다. LangGraph 를 쓰고 Supervisor 가 있어서 그렇게 보일 뿐이다.

| | 작업 | 크기 | 의존 |
|---|---|---|---|
| A1 | `LLMClient` 에 tool use 추가 (anthropic / openai / **mock**) | 중간 | — |
| A2 | `agents/tools.py` — `core/` 함수를 도구로 노출 | 작음 | A1 |
| A3 | 실행 루프 + 반복 상한 + 실패 fallback | 중간 | A2 |
| A4 | trace 노출 — 어떤 도구를 어떤 인자로 불러 무슨 값이 나왔는가 | 작음 | A3 |
| A5 | Supervisor 연결 (정의만 되어 있는 `RESULT` intent 소비) | 작음 | A3 |
| A6 | 대화 화면을 **결과 이후로** 확장 (웹 + Streamlit) | 중간 | A5 |
| A7 | 도구 출력에 없는 숫자 차단 — `verify_numbers` 재사용 | 작음 | A3 |

**A1 의 mock 구현을 빼면 안 된다.** 키 없이 전체 흐름을 테스트하는 것이 이 저장소의
규칙이고, CI 와 발표 당일 안전망이 거기 걸려 있다.

**A4 가 심사 포인트다.** 에이전트가 자율적으로 움직이면서도 모든 숫자에 출처가
남는다. 사기 탐지가 "걸린 표현"을 그대로 보여주는 것과 같은 원리다.

`core/` 가 순수 함수라서 도구화가 거의 공짜라는 점이 W1 설계의 배당금이다.
`prescribe.py` 가 표시 문자열과 원시 숫자를 함께 싣는 것도 이 단계를 위한 준비다.

## B. 신뢰 보강 — 우리 숫자 자체를 환산 대상으로

| | 작업 | 크기 |
|---|---|---|
| B1 | 민감도 분석 — "물가 2.3→3.0%면 고갈이 ○년 앞당겨집니다" | 작음 |
| B2 | 건강보험료 피부양자 탈락 절벽 | 중간 |

B1 은 A2 보다 **먼저** 하는 편이 낫다. 그러면 도구 등록 때 함께 올라간다.
따로 만드는 것이 아니라 도구가 하나 느는 것이다.

## C. 데이터 최신화 — 코드로 해결되지 않는 항목

| | 작업 |
|---|---|
| C1 | `policy_facts.yaml` ISA 파라미터를 기재부 원문으로 확인 |
| C2 | 연기 7.2% / 조기 6% 가산·감액률을 국민연금법 원문으로 확인 |

C1 은 "연 9만 9,000원이 상한"이라는 핵심 문장이 직접 걸려 있어 발표 전 필수다.

## D. 안정화 + 발표 (원 계획서 W8)

| | 작업 |
|---|---|
| D1 | 5장면 데모 스크립트 고정 (말할 숫자 · 클릭 순서 · 대사) |
| D2 | 예외 fallback 점검 — 세션 소멸, 네트워크 끊김, TTS 미지원 |
| D3 | 발표 자료 — 아키텍처, 의도적 이탈, 안 만든 것과 이유 |
| D4 | 버퍼 |

---

## 순서

```
B1 → A1 → A2 → A3 → A4 → A7 → A5 → A6 → [C1·C2 병렬] → D1~D4
```

B1 으로 도구를 하나 더 확보하고, A1~A3 으로 루프를 세우고, A4/A7 로 신뢰 장치를
붙인 뒤 화면에 연결한다. C 는 언제든 병렬로 가능하고, D 의 버퍼는 반드시 남긴다.

---

## 보류 — 축을 바꾸지 않는 것들

발표에서 "왜 안 했나" 질문이 들어올 항목이므로 **의도적 결정임을 남겨 둔다.**

| 항목 | 왜 미루나 |
|---|---|
| 주택연금(역모기지) | 레버 하나가 늘 뿐 축이 바뀌지 않는다. 공사 공시표(월지급금 예시표)를 확보하면 그때 도구로 붙인다. 산정식을 근사로 지어내지 않는다 |
| 블록 부트스트랩 몬테카를로 | 꼬리 위험 반영은 옳지만, "변동성 0이면 결정론적 결과와 일치"라는 두 엔진 정합성 테스트를 다시 세워야 한다 |
| 인출 순서 최적화 | 엔진을 단일 pool 에서 계좌 단위로 쪼개야 한다 |
| 상품 추천·랭킹 | 상품 데이터와 랭킹 학습 데이터가 없다. "상품 유형까지만"이 이미 내린 결정이다 |
| 가구(부부) 단위 | 유족연금까지 들어가면 모델 복잡도가 급증한다 |
| ⑨ 능동 알림 풀버전 | 유저 DB 가 선행되어야 한다. B1 을 "내 계획이 깨지는 조건" 화면으로 재포장하는 것이 정직한 축소판이다 |
