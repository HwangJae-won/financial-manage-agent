# 은퇴 시니어를 위한 내 자산 AI 네비게이터

퇴직 전후 55~64세 중장년층을 대상으로, 자산·소득·연금을 종합 분석해
"그래서 지금 무엇을 해야 하는가"를 알려주는 금융 의사결정 지원 AI.

## 설계 원칙

> **`core/`는 LLM을 절대 호출하지 않는다.**
> LLM은 (a) 사용자 입력을 구조화하고 (b) 계산 결과를 설명하는 양 끝단에만 존재한다.

금융 서비스에서 숫자를 LLM이 만들면 환각 리스크를 통제할 수 없다.
모든 계산은 `core/`의 순수 파이썬 함수가 담당하고, LLM에는 "제시된 숫자만
인용하고 직접 계산하지 말 것"을 강제한다.

## 이 서비스의 축

> **남이 하는 말이 나에게 얼마인지 계산해서,
> 대부분의 경우 "그건 당신에게 중요하지 않습니다"라고 정직하게 말하는 것.**

만든 기능은 개별 항목이 아니라 전부 같은 축의 사례다. "당신에겐 영향 없습니다"라고
말할 인센티브가 있는 주체가 시장에 없다 — 금융사는 상품을 팔아야 하고, 뉴스는 클릭이
필요하고, 챗봇은 그럴듯한 답을 해야 한다.

| 입력 | 세상이 하는 말 | 이 서비스가 하는 말 |
|---|---|---|
| 사기 문자 | "제도 바뀌니 지금 갈아타세요" | 연 **9만 9,000원**이 상한입니다 |
| 뉴스 | "ISA 세제 개편" | **발표(1/5단계)**입니다. 고객님껜 연 **2만 6,706원** |
| 진단 결과 | "69세 고갈" | 월 **113만원** 줄이면 95세까지 갑니다 |
| 안정도 점수 | "98점 양호" | 여유는 **월 5만원**뿐입니다 |
| 퇴직금 | "세금 떼면 얼마 안 남아요" | 근속 32년이면 실효 **1.54%**, 308만원입니다 |
| 예금 갈아타기 | "금리 높은 데로 옮기세요" | 이자 **347만원** 더 받는 순간 건보료가 생깁니다 |
| 국민연금 추가납부 | "더 내면 더 받습니다" | 월 40만원 받으실 분껜 **800만원 손해**입니다 |
| 상담 AI 답변 | (그럴듯한 숫자) | 계산에 없는 숫자면 **그 답변을 내보내지 않습니다** |

## 기능

기획서 9개 기능 **전부**와, 축을 세우면서 추가한 것들.

### 진단 — 지금 어떤 상태인가

| 기능 | 무엇을 답하나 | 모듈 |
|---|---|---|
| 대화형 프로파일링 ① | 12개 질문으로 자산·소득·연금을 모은다. **모르면 추측하지 않고 물어본다** | `agents/profiling.py` |
| 자산지도 ② | "얼마 있나"가 아니라 **"어떤 목적으로 얼마 동안 쓸 것인가"** | `core/asset_map.py` |
| 캐시플로우 시뮬레이션 ③ | 소득공백기를 넘길 수 있나. 금융자산이 언제 바닥나나 | `core/cashflow.py` |
| 몬테카를로 | 수익률이 흔들릴 때 자산이 남아있을 확률 | `core/montecarlo.py` |
| 은퇴 재무 안정도 | 100점 만점. **파산이 확실하면 점수에 상한을 건다** | `core/risk_score.py` |
| 시나리오 비교 | 안정·균형·성장 3안. 하나의 정답을 권하지 않는다 | `core/scenarios.py` |

### 처방 — 그래서 무엇을 하면 되나

| 기능 | 무엇을 답하나 | 모듈 |
|---|---|---|
| 처방 엔진 | "월 **187만원**으로 줄이면 95세까지 유지됩니다". 같은 엔진을 역방향으로 | `core/prescribe.py` |
| 퇴직금 수령 방식 ⑤ | 일시금 vs 연금. 퇴직소득세를 **제도 구조 그대로** 계산 | `core/severance.py` |
| 건강보험 피부양자 절벽 | 지금 0원, **2031년부터 연 80만원**. 이자 347만원만 늘면 그 순간 발생 | `core/health_insurance.py` |
| 국민연금 임의계속가입·추납 | 더 낼지 말지. **늘어난 연금에서 건보료를 빼고 남는 것**으로 답한다 | `core/national_pension.py` |
| 일회성 큰 지출 | 자녀 결혼자금 5,000만원 → 고갈 69세에서 **66세**로 | `core/models.py` |
| 민감도 분석 | 우리 가정이 틀리면 결과가 얼마나 흔들리나 (자기검증) | `core/sensitivity.py` |

### 지켜주기 — 남이 하는 말 확인하기

| 기능 | 무엇을 답하나 | 모듈 |
|---|---|---|
| 금융사기·불완전판매 탐지 ⑦ | 받은 문자의 위험 신호. **어떤 표현이 걸렸는지 그대로** 보여준다 | `agents/fraud.py` |
| 정책 영향 분석 ④ | 제도 변화가 **내 자산 기준으로 얼마인가** | `core/policy.py` |
| 신뢰 표시 ⑧ | 발표 / 입법예고 / 국회통과 / 공포 / 시행을 구분한다 | `data/policy_facts.yaml` |
| 가족 공유 리포트 | 가족과 함께 볼 한 장. **기한이 있는 것**과 **안 해도 되는 것**을 나눈다 | `core/family_report.py` |
| 은퇴 타임라인 · 행동 경로 | 기한을 조건문이 아니라 **날짜로**. 어디서 어떻게 신청하는지까지 | `core/timeline.py` |
| 능동 알림 ⑨ | 다시 오셨을 때 그동안 무엇이 다가왔는지 | `core/timeline.py` |

### 상담 — 결과를 두고 이어서 묻기

| 기능 | 무엇을 답하나 | 모듈 |
|---|---|---|
| 도구를 쥔 상담 에이전트 | "생활비 50만원 줄이면요?" → **계산을 다시 돌려서** 답한다 | `agents/advisor.py` |
| 실행 기록(trace) 노출 | 어떤 도구를 어떤 인자로 불러 무슨 값이 나왔는지 화면에 | `web/static/app.js` |
| 지어낸 숫자 차단 | 도구 출력에 없는 숫자가 있으면 **그 답변을 버린다** | `agents/advisor.py` |
| Supervisor 라우팅 | 프로파일링 / 상담 / 사기확인 — 한 창구로 들어와 여기서 갈린다 | `agents/graph.py` |

같아야 한다"는 테스트로 강제한다.

## 계산 규약 (발표 대응용)

1. 시뮬레이션은 **퇴직 시점부터** 시작한다. 퇴직 전 축적은 반영하지 않는다(보수적).
2. 투자수익은 **연초 잔액 기준**, 인출은 연말 발생으로 본다.
3. 생활비는 매년 물가상승률만큼 증가. 국민연금은 법정 물가연동 반영.
   기타소득(임대·근로)은 물가에 연동하지 않는다(보수적).
4. 세금은 이자·배당 성격 수익(현금성·채권)에만 부과. 국내주식 양도차익은
   소액주주 비과세 현실을 반영해 과세하지 않는다.
5. 퇴직 연도와 연금 개시 연도는 개월 단위로 안분한다.
6. **세금·건강보험료는 실효세율 근사다. 화면에 "참고용" 고지가 필수다.**
7. 국민연금을 법정 개시연령보다 미루면 연 7.2% 가산, 앞당기면 연 6% 감액하며
   양쪽 모두 최대 5년이다. 조정된 금액은 평생 유지된다.
8. 몬테카를로는 자산군 간 상관계수 0, 연도 간 독립, 정규분포를 가정한다.
   실제 시장의 상관과 두꺼운 꼬리를 반영하지 않으므로 꼬리 위험을 과소평가할 수 있다.

가정값의 근거는 전부 `data/assumptions.yaml`의 주석에 있다.

## 기획서에서 의도적으로 벗어난 지점

**리스크 스코어에 지속가능성 상한을 추가했다.** 기획서의 가중치는 단기 항목
(소득공백기 30% + 유동성 25%)에 55%가 몰려 있어, "지금은 현금이 넉넉하지만
69세에 파산이 확실한" 사람에게도 87점이 나온다. 화면에 *양호 87점*과
*만 69세 자산 고갈*이 나란히 뜨면 사용자는 무엇을 믿어야 할지 알 수 없고,
심사에서도 바로 지적받을 지점이다.

가중치 자체는 기획서를 그대로 두되, 시뮬레이션이 파산을 가리키면 종합 점수가
그 사실을 넘어설 수 없게 상한을 뒀다 (75세 이전 고갈 → 40점, 85세 이전 → 60점).
또 `장기소득` 항목은 연금/생활비 비율뿐 아니라 실제 고갈 시점을 함께 반영한다.

가중치를 바꾸는 편이 낫다고 판단되면 `core/risk_score.py`의 `WEIGHTS`와
`_sustainability_cap` 을 함께 조정할 것.

## 검증 기준

기획서 예시 인물(2026년 12월 퇴직, 금융자산 2.2억, 월 생활비 300만,
국민연금 월 150만·2030년 개시)에 대해 엔진이 산출하는 값:

- 소득공백기 **4년**
- 생활비 충당 가능 **6.2년** ← 기획서의 "약 6.2년"과 일치
- 연금 개시 시점 잔액 **1억 1,855만원**
- 금융자산 고갈 **2035년(만 69세)**
- 은퇴 재무 안정도 **40/100 (부족)** — 원점수 87점에 지속가능성 상한 적용

이 숫자들은 `tests/test_demo_regression.py`에 고정되어 있다.
가정값을 바꿔서 깨지면, 테스트를 고치지 말고 **바뀐 숫자가 의도한 것인지 먼저 확인**할 것.

이 값들은 **LLM 을 바꿔도 같아야 한다.** 계산은 `core/` 가 하고 모델은 슬롯을
채울 뿐이기 때문이다. 다르게 나오면 모델이 계산을 틀린 게 아니라 **추출을 틀린
것**이고, 규칙 파서(`agents/mocks.py`)의 결과와 나란히 놓으면 어느 슬롯인지 바로
보인다. 로컬 Llama-3.1-8B 로 12턴을 3회 반복해 세 값이 모두 일치하는 것을 확인했다.

## LLM 연결

`.env` 한 줄로 프로바이더를 바꾼다. 키가 없으면 자동으로 mock 이 되고,
설정이 잘못돼도 앱은 죽지 않고 mock 으로 떨어진다.

```
FINAGENT_LLM_PROVIDER=anthropic   # anthropic | openai | local | mock (비우면 자동)
ANTHROPIC_API_KEY=sk-ant-...
```

연결 확인: `python scripts/smoke_llm.py`

**구독은 API 사용권이 아니다.** Claude Max 도 ChatGPT Plus 도 API 결제는 별도다
(console.anthropic.com / platform.openai.com). OpenAI 는 모델 ID 라인업이 자주
바뀌므로 기본값을 두지 않았다 — `OPENAI_MODEL` 을 직접 지정해야 한다.

### 로컬 모델 — API 키 없이 GPU 로

```bash
bash scripts/serve_local.sh          # vLLM (OpenAI 호환) 기동
```
```
FINAGENT_LLM_PROVIDER=local
LOCAL_BASE_URL=http://127.0.0.1:8001/v1
LOCAL_MODEL=NousResearch/Meta-Llama-3.1-8B-Instruct
```

**새 클라이언트를 만들지 않았다.** vLLM 이 OpenAI 호환 API 를 주므로 `OpenAIClient`
에 `base_url` 만 더해 그대로 쓴다. 모델을 바꿀 때도 위 두 줄만 바뀐다.

vLLM 은 **별도 conda 환경**에 둔다. 같은 환경에 넣으면 pydantic·fastapi·numpy 를
자기 버전으로 끌어와 기존 테스트가 깨진다. 앱과는 HTTP 로만 붙으므로 문제없다.

측정 결과 (Llama-3.1-8B, A100 1장):

| | 로컬 모델 | mock |
|---|---|---|
| 도구 선택 정확도 | 7/7 | 7/7 |
| 예시 인물 숫자 재현 | 일치 (3회 반복) | 일치 |
| 응답 시간 중앙값 | 1.6초 | 6ms |

`python scripts/eval_local.py` 로 언제든 다시 잰다.

### LLM 이 숫자를 지어내지 못하게 하는 **세** 겹의 방어

1. **사전** — 프롬프트에 계산 결과를 사실 목록으로 넣고 그 안의 숫자만 쓰라고 지시
2. **사후 검증** — 생성된 문장의 모든 숫자가 사실 목록에 있는지 기계적으로 검사
   (`agents/explain.py` 의 `verify_numbers`)
3. **차단** — 상담 답변은 걸리면 **내보내지 않는다** (`agents/advisor.py`)

2번이 핵심이다. 프롬프트 지시는 지켜지지 않을 수 있지만 검사는 확실하다.

3번은 브리핑과 상담을 다르게 다룬다. **브리핑은 표시만 하고 원문을 내보내지만
상담 답변은 막는다.** 브리핑은 화면의 계산 결과와 대조할 수 있지만, 상담 답변은
대조할 대상이 화면에 없어서 틀린 숫자가 그대로 사용자의 판단이 된다. 한 번은
스스로 고칠 기회를 주고, 그래도 남으면 계산된 값만으로 만든 문장으로 대체한다.

실제로 로컬 모델에서 걸렸다 — "생활비를 50만원 줄이면"에 모델이 계산에 없는
"35"(년)를 말해 답변이 버려졌다. mock 에서는 한 번도 걸리지 않던 경로다.

### 작은 모델의 금액 자릿수는 규칙 파서로 교차검증한다

8B 급 모델은 "5억"을 50억으로, "300만원"을 3천만원으로 적는다. 총자산이 7억에서
57억이 되어도 화면은 멀쩡해 보이는 **조용한 오류**다. 프롬프트로 대부분 잡히지만
매 실행마다 다른 슬롯에서 미끄러져 닫히지 않는다.

그래서 역할을 나눴다. **어느 항목인지는 LLM 이 판단하고, 숫자가 몇 자리인지는
글자를 그대로 읽는 규칙 파서가 판단한다.** 두 값이 정확히 10의 거듭제곱 배로
다를 때만 고치고, 그 외의 불일치는 서로 다른 것을 읽은 것이므로 건드리지 않는다.
(`agents/profiling.py` 의 `reconcile_amounts`)

## 금융사기 탐지 (기능 ⑦)

세 겹으로 본다:

1. **규칙** (`data/fraud_rules.yaml`) — 레드플래그 9종. LLM 없이 동작하고,
   **어떤 표현이 걸렸는지 그대로 보여준다.** 근거를 댈 수 없는 경고는
   시니어 사용자에게 무의미하다.
2. **정책 대조** (`data/policy_facts.yaml`) — "제도가 바뀌었으니 갈아타라"는 주장을
   공식 팩트시트와 맞춘다. **발표 / 입법예고 / 국회통과 / 공포 / 시행**을 구분하는
   것이 기획서의 핵심 차별점이다. 뉴스는 이걸 구분하지 않는다.
3. **프로필 연결** — "고객님은 ISA에 5,000만원을 보유하고 계십니다"처럼
   실제 자산과 엮는다. 보유하지 않은 상품을 근거로 든 권유는 그 자체가 신호다.

측정된 동작 (기획서 예시 사기 문자):

| | 결과 |
|---|---|
| 사기 문자 | 위험 · 신호 6개 검출 (원금보장+고수익, 비현실 수익률, 재촉, 비공식 채널, 제도 빙자, 비밀 유지) |
| 정상 은행 안내 | 낮음 · **오탐 0** ("연 3.2%"는 정상 범위로 통과) |

정밀도가 재현율만큼 중요하다. "맨날 위험하다고만 한다"고 느끼면 사용자는
경고를 무시하게 되고, 그때부터 이 기능은 없는 것과 같다.

⚠️ `data/policy_facts.yaml` 은 **예시 데이터**다. 발표 전에 원문으로 최신화할 것.

## 퇴직금, 일시금과 연금 중 어느 쪽인가 (기능 ⑤)

타겟이 **지금 당장 내려야 하는 결정**이다. 그런데 그전까지의 엔진은 퇴직금 2억을
그냥 현금 2억으로 봤다.

이 서비스에서 유일하게 실효세율 근사가 아니라 **제도의 계산 구조를 그대로** 따라가는
세금이다. 퇴직소득세는 근속연수공제가 매우 커서 평균 세율 하나로 뭉개면
"장기근속자는 퇴직소득세가 거의 없다"는 중요한 사실이 사라진다.

| 퇴직금 2억 기준 | 세액 | 실효세율 |
|---|---|---|
| 근속 5년 | 3,570만원 | 17.9% |
| 근속 32년 | **308만원** | **1.54%** |
| 근속 40년 | 193만원 | 0.97% |

세액뿐 아니라 **납부 시점**까지 비교한다. 일시금은 퇴직할 때 한 번에, 연금은 받을
때마다 나눠 낸다. 늦게 내는 만큼 그 돈이 더 오래 운용되는데, 세율표만 봐서는 안
보이고 실제로는 이쪽 효과가 더 클 때도 있다. 그래서 **두 경우를 각각 끝까지
시뮬레이션한다.**

**근속연수를 모르면 계산하지 않고 물어본다.** 5년과 40년은 세금이 18배 차이라
기본값으로 채우면 사용자가 그 숫자를 믿게 된다.

## 건강보험 피부양자 절벽

퇴직하면 건강보험료가 0원에서 연 수백만원이 된다. 두 가지 이유로 이 서비스의 축에
정확히 맞는다.

**1. 계단이다.** 금융소득이 연 1,000만원 **이하면 합산에서 아예 빠지고, 1원이라도
넘으면 전액이 들어간다.** 이자를 1만원 더 받았다고 연 수백만원이 생길 수 있다.
"예금 금리 높은 상품으로 갈아타세요"라는 말이 이 구간의 고객에게 실제로 얼마인지는
이렇게 계산해야만 나온다. 기획서 예시 인물은 여유가 **347만원(수익률 1.58%p)** 남았다.

**2. 가만히 있어도 다가온다.** 국민연금은 물가에 연동돼 매년 오르는데 피부양자
소득기준 2,000만원은 그대로다. 지금 통과해도 몇 년 뒤 넘는다. 그래서 한 시점이
아니라 **연도별로 판정하고 넘는 해를 찾는다** — 예시 인물은 지금 0원, **2031년(만
65세)부터 연 80만 7,516원**.

**재산분 보험료는 넣지 않았다.** 점수표를 확보하지 못해 근사식을 지어내지 않았다
(주택연금과 같은 결정). 따라서 이 금액은 **하한**이고, 그 사실과 오차의 방향을
화면에 함께 낸다.

## 국민연금을 더 낼까 — 임의계속가입·추납

연기·조기가 **"언제 받을까"**의 레버라면 이쪽은 **"얼마나 쌓았나"**의 레버다.
가입기간이 모자란 사람에게는 앞의 레버가 아무 의미가 없다 — 받을 연금 자체가 없다.

여기에도 계단이 있다. **가입 119개월과 120개월은 연속적이지 않다.** 119개월이면
노령연금이 평생 0원이고 반환일시금만 받는다(국민연금법 제61조).

이 기능의 값어치는 "연금이 늘어납니다"에 있지 않다. **연금을 늘리면 건강보험
피부양자에서 더 빨리 탈락한다.** 공적연금소득은 피부양자 판정에서 전액이 합산되기
때문이다. 그래서 수단마다 세 가지를 같은 기준(퇴직 시점 화폐)으로 놓고 순효과를 낸다.

| 인물 | 결과 |
|---|---|
| 예시 인물 (연금 150만원) | 임의계속가입 2,665만원 → 연금 +18만 7,500원, 건보료 +279만원 → **순 4,049만원 이득** |
| 연금 140만원인 사람 | 피부양자 탈락이 **2034 → 2031년**, 3년 앞당겨짐 |
| 연금 40만원인 사람 | 2,665만원 내고도 **800만원 손해** → "지금 그대로"를 권한다 |

**A값·B값을 지어내지 않는다.** 공단 예상연금액을 기준점으로 삼고 기본연금액 산식의
가입기간 계수(별표 1) 비율만 쓴다. 그래서 **가입월수를 모르면 계산하지 않는다.**

## 가족에게 보여줄 한 장

시니어의 금융 결정은 혼자 내려지지 않는다. 자녀가 "그거 하지 마세요" 하고, 배우자가
"옆집은 했다던데" 한다. 그런데 그전까지 만든 것은 전부 **본인 화면**이었다.

가족이 읽는다는 전제가 내용을 바꾼다.

- **기한이 있는 것을 맨 위로.** 임의계속가입은 신청 기한을 놓치면 끝이고, 자산
  배분은 다음 달에 해도 된다. 가족이 도울 수 있는 것은 주로 앞쪽이다
- **하지 않아도 되는 것을 명시한다.** 가족이 가장 많이 하는 개입이 "뭐라도 해야
  하는 것 아니냐"이기 때문이다
- **가정한 값과 계산하지 않은 것을 함께 낸다.** 가족은 본인보다 더 꼼꼼히 읽는다

카톡으로 보낼 평문도 만든다. 화면을 캡처해 보내면 숫자만 남고 기한과 한계가 사라진다.

## 세션과 상담 기록 저장

세션이 메모리 dict 였을 때는 프로세스가 죽으면 상담이 통째로 사라졌고, 사용자는
12개 질문에 처음부터 다시 답해야 했다. sqlite 한 파일로 옮겼다 — 서버 프로세스가
필요 없어 **발표 당일 DB 가 안 떠서 데모가 죽는 경로**를 만들지 않는다.

`storage/` 는 `core/` 도 `agents/` 도 모르고, 반대로 저장소도 그것들을 모른다.
**평범한 dict 만 주고받는다.**

기록의 두 번째 용도가 있다. `messages`·`advice`·`tool_runs` 세 표가 **모델 평가의
재료**다. 어떤 도구를 불렀는지(정확도), 숫자 차단이 몇 번 걸렸는지, 응답이 얼마나
걸렸는지가 쌓인다. 그전까지는 이 기록이 메모리에만 있다가 사라져서 "실제 모델이
어땠나"를 추측으로만 답할 수 있었다.

유저는 만들되 **인증은 만들지 않았다.** 브라우저의 uuid 하나가 신원의 전부이고
비밀번호도 이메일도 받지 않는다. 데모 범위에서 인증을 흉내 내면 안전하지 않은 것을
안전한 것처럼 보이게 만들 뿐이다. 대신 자산·소득이 저장된다는 사실을 화면에 적는다.

**저장 실패가 대화를 끊지 않는다.** 저장소는 편의 기능이지 서비스의 전제가 아니다.

## 가정값이 낡았는지 확인하기

`data/assumptions.yaml` 의 91개 값 중 **매년 바뀌는 것은 5~6개**뿐이고, 바뀌는 달도
정해져 있다 — 1월(건강보험료율), 7월(국민연금 기준소득월액). 검색이 아니라 달력의
문제다.

```bash
python scripts/check_assumptions.py
```

`data/sources.yaml` 에 값마다 출처·유효기간·추출 패턴을 두고, 기간이 지난 값을
법제처 국가법령정보 API 로 원문과 대조해 **보고만 한다.**

**자동 반영은 하지 않는다.** 재산분 점수표를 못 구해 근사식을 만들지 않았고 주택연금
산정식도 지어내지 않은 프로젝트에서, 긁어온 숫자를 검증 없이 반영하면 앞뒤가 맞지
않는다. 잘못된 자동 갱신은 보이는 낡음보다 나쁘다 — 낡은 값은 "낡았다"는 사실이
참이지만, 잘못 갱신된 값은 "최신이다"라고 거짓말을 한다.

추출값이 타당 범위를 벗어나면 **"못 찾음"으로 처리한다.** 틀린 값을 보고하는
검사기는 없느니만 못하다.

⚠️ 첫 실행에서 국민연금 기준소득월액 상한이 **617만원 → 659만원**(2026.7 시행)으로
낡았음이 확인됐다. 아직 반영 전이다.

## 일회성 큰 지출

이 연령대의 계획을 실제로 무너뜨리는 것은 매달의 생활비가 아니라 **한 번에 나가는
큰돈**이다. 자녀 결혼자금, 목돈 의료비, 주택 수리. 매년 일정한 생활비만 가정하면
"그래서 결혼자금 5,000만원은 어디에 반영됐나요"라는 질문에 답할 수 없다.

기획서 예시 인물에게 2029년 자녀 결혼자금 5,000만원을 넣으면:

| | 고갈 시점 |
|---|---|
| 지출 없음 | 만 69세 |
| 결혼자금 5,000만원 | **만 66세** (3년 앞당겨짐) |

금액은 **퇴직 시점 기준**으로 본다. 월 생활비와 같은 규약이라 발생 연도까지
물가상승률만큼 커진다(보수적).

프로파일링 질문은 12개 그대로 두었다. 질문을 하나 늘리는 것보다 **에이전트가
대화로 다루는 편**이 이 기능에 맞다 — "내후년에 결혼자금 5천만원이 나가면요?"

## 처방 엔진 — "그래서 무엇을 하면 되나"

W7 까지의 엔진은 **진단만** 했다. "만 69세에 금융자산이 고갈됩니다"에서 멈춘다.
`core/prescribe.py` 는 같은 엔진을 **역방향으로** 써서 그다음을 답한다.

    "월 생활비를 187만원으로 줄이시면 만 95세까지 유지됩니다."

레버 세 개를 각각 역산한다. 기존 `simulate()` 위에 얹는 구조라 계산 규약과
회귀 테스트가 그대로 유지된다.

| 레버 | 탐색 방법 | 이유 |
|---|---|---|
| 월 생활비 | 이분 탐색 | 줄일수록 유리 — 단조 |
| 국민연금 개시 시기 | **전 구간 계산** | 단조가 아니다 (아래) |
| 기타 월소득 | 이분 탐색 | 늘릴수록 유리 — 단조 |

### 연금 레버에 이분 탐색을 쓰면 안 되는 이유

연기하면 수령액은 늘지만 그때까지 자산을 더 헐어야 한다. 어느 쪽이 유리한지는
사람마다 뒤집힌다. 기획서 예시 인물(DEMO)은 **연기가 오히려 불리하다**:

| 개시 연령 | 월 수령액 | 고갈 |
|---|---|---|
| 만 62세 (조기) | 132만원 | 만 70세 |
| 만 64세 (법정) | 150만원 | 만 69세 |
| 만 69세 (연기) | 204만원 | 만 67세 |

자산이 빠르게 줄어드는 사람에게는 "지금 들어오는 현금"이 더 중요하다.
그래서 가능한 연령을 전부 계산해 비교한다. 조기 수령을 권할 때는 **감액이 평생
유지된다**는 경고가 반드시 함께 나간다.

조기노령연금은 소득이 있는 동안 받을 수 없으므로 퇴직 이전 연령은 후보에서 제외한다.

### 측정된 동작

| 인물 | 결과 |
|---|---|
| DEMO (69세 고갈) | 생활비 **월 113만원↓(37.7%)** 또는 추가수입 **월 162만원** |
| DIVERSIFIED (고갈 없음) | 여유는 **월 5만원뿐** — 98점이라는 점수보다 빠듯하다 |

DIVERSIFIED 의 여유가 월 5만원이라는 것은 안정도 98점만 보고는 알 수 없는
사실이다. 처방 엔진이 없었으면 드러나지 않았을 값이다.

### 검증 방식

처방이 틀리면 진단이 틀린 것보다 나쁘다 — 사용자가 그 말을 믿고 생활을 바꾼다.
그래서 **왕복 검증**을 건다: 답한 값을 엔진에 다시 넣어 정말 목표까지 버티는지
확인하고, 한 칸(만원) 더 쓴 값은 실패하는지도 확인한다. 필요 이상으로 졸라매게
만드는 답도 틀린 답이다. 이분 탐색의 결과는 완전탐색 결과와 대조한다.

답은 항상 만원 단위다. "2,413,271원으로 줄이세요"는 사람이 쓸 수 없는 답이다.

### 하지 않는 것

조합 탐색(생활비도 줄이고 연금도 미루고)은 이 모듈에서 하지 않는다. 경우의 수가
곱으로 늘고, 무엇보다 **무엇을 포기할지는 사용자가 정할 문제**다. 레버별로 얼마가
필요한지만 정확히 답하고, 조합은 대화 에이전트에게 맡긴다.

## 민감도 분석 — 우리 숫자 자체를 흔들어 본다

이 서비스가 내놓는 모든 숫자는 가정 위에 있다. 심사·발표에서 "그 가정이 틀리면요?"는
반드시 나오는 질문이고, **답을 준비하는 것보다 화면에 미리 띄워두는 편**이 낫다.

남의 말을 "내 자산 기준 얼마"로 환산해 왔으니, 우리 출력도 같은 방식으로 환산한다.

### 측정된 동작

| 가정 | DEMO 흔들림 | DIVERSIFIED 흔들림 |
|---|---|---|
| 월 생활비 (±10%) | **4년** | **8년** |
| 물가상승률 (±0.7%p) | 1년 | 5년 |
| 투자 기대수익률 (±1.0%p) | 1년 | 4년 |
| 금융자산 평가액 (±10%) | 2년 | 4년 |
| 국민연금 수령액 (±10%) | 1년 | 3년 |

**두 인물 모두 월 생활비가 결과를 지배한다.** 사용자가 기억으로 답하는 값이라
오차가 크면서 지배력도 가장 크다 — "이 값을 정확히 아는 것이 가장 중요합니다"라고
말할 근거가 된다.

그리고 DIVERSIFIED 는 **안정도 98점 '양호'인데 생활비가 10% 늘면 만 87세에 고갈된다.**
점수만 보고는 알 수 없는 사실이고, 이 분석이 존재하는 이유다.

### 한계 (고지 필수)

한 번에 한 가지 가정만 흔든다(일변량). 가정들이 동시에 나빠지는 경우는 반영되지
않으므로 실제 최악은 이보다 나쁠 수 있다. 이 문장은 `caveat` 로 화면에 항상 나간다.
동시에 움직이는 상황은 몬테카를로가 다룬다.

### 구현 주의

`load_assumptions()` 는 `lru_cache` 로 전역 공유된다. 흔들어 보는 과정에서 원본을
건드리면 **이후 모든 계산이 조용히 틀어진다.** 반드시 `model_copy(deep=True)` 로
복사해서 바꾸며, 이를 테스트로 강제한다(`test_the_shared_assumptions_are_not_mutated`).

## 정책 영향 분석 (기능 ④·⑧, W7)

기획서의 정책 RAG(크롤링 + Vector DB + 시점 관리)는 문서 수집이 별도 프로젝트급이라
범위 밖이다. 대신 **ISA 세제 개편안 한 건만** 골라 계산 끝까지 연결했다.
뉴스 요약은 포털에도 있다. **"고객님 자산 기준으로 연 ○○원"** 이 나와야 이 기능이
존재할 이유가 생긴다.

### 어떻게 계산하나

팩트시트의 세제 파라미터를 캐시플로우 엔진에 주입해 **현행 제도와 개편안을 같은
기준으로** 각각 재시뮬레이션하고 차이만 본다. 세제 외의 규약(수익 시점, 물가연동,
퇴직월 안분)은 두 시뮬레이션이 공유하므로 결과 차이는 오직 세제 차이다.

`simulate(tax_model=...)` 이 그 자리다. 넘기지 않으면 기존 규약 그대로라
W1~W6 의 숫자는 한 개도 바뀌지 않는다 (`test_default_tax_model_changes_nothing`).

### 측정된 동작

| 인물 | 결과 |
|---|---|
| DEMO (ISA 없음) | **영향 없음** — "ISA 계좌를 보유하고 계시지 않습니다" |
| DIVERSIFIED (ISA 5,000만원) | 연 **2만 6,706원** · 은퇴 기간 전체 **26만원** 절감 |
| ISA 4억으로 늘려도 | 연 **9만 8,621원** — 상한에 막힌다 |

**결론이 "영향이 거의 없습니다"라는 점이 이 기능의 핵심이다.** 사기 문자는 늘
"제도가 바뀌니 지금 갈아타라"고 말한다. 실제 영향을 원 단위로 계산해 보여주는 것이
그 주장에 대한 가장 값싸고 확실한 반박이다.

### 구조적 상한 — 이 기능에서 가장 강한 문장

비과세 한도만 올리는 개편이라면 절감액은 **(한도 증가분 ÷ 의무가입기간) × 분리과세율**
을 넘을 수 없다. 보유액이 아무리 커도 그렇다. 지금 파라미터로는 **연 9만 9,000원**이다.

> "이 개편안으로 줄어드는 세금은 보유액이 아무리 크셔도 연 9만 9,000원을 넘지 않습니다."

개인의 자산을 몰라도 말할 수 있는 문장이고, 갈아타기 권유에 대한 답이 된다.
분리과세율까지 바뀌는 개편이면 상한이 없어지므로 `max_annual_saving` 은 `None` 이 된다.

### 신뢰 표시 (⑧)

모든 정책성 출력에 **출처 · 확정여부(5단계 중 몇 번째) · 시행일 · 확인일**이 붙는다.
시행되지 않은 건에는 "아직 확정되지 않았습니다" 문구가 강제된다 (`PolicyFact.notice`).

```
⚠️ 발표 (미확정) | ISA 세제 개편 논의
출처: 기획재정부 세법개정안 · 확정여부: 발표(1/5단계) · 시행일 미정 · 확인일: 2026-08-13
```

뱃지 문구는 서버가 완성해서 보낸다. 사기 확인 화면과 제도 변화 화면이 **같은 문자열**
을 쓰기 위해서다 — 같은 제도가 두 화면에서 다르게 표시되면 그 자체가 불신 요인이다.

### 알려진 한계

- ISA 가 전체 금융자산에서 차지하는 비중이 은퇴 기간 내내 유지된다고 본다.
  계좌 간 이동이나 만기 재가입은 반영하지 않는다.
- 기본 분석 화면의 세금은 ISA 비과세 혜택을 반영하지 않은 보수적 값이다.
  이 비교는 현행·개편안 **양쪽 모두에** ISA 세제를 적용해 차이만 본다.
- 계약기간 총액 한도를 의무가입기간으로 나눠 연 환산한다. 해마다 한도가 새로
  채워진다고 보면 실제보다 유리해지므로 이쪽이 보수적이다.

## Supervisor — 대화의 단일 창구

**규칙이 먼저, LLM 은 애매할 때만.** 붙여넣은 사기 메시지는 길고 광고성 표현이 있어
구조적으로 알아볼 수 있으므로 LLM 을 부를 이유가 없다 — 빠르고, 공짜고, 왜 그렇게
분류했는지 설명된다. 분류에 실패해도 기본 경로로 보내 대화가 끊기지 않는다.

사용자가 무엇을 말하든 **입구는 하나**다. 같은 엔드포인트인데 상태에 따라 갈린다.

| 상황 | 어디로 |
|---|---|
| 대화 진행 중 | 프로파일링 — 다음 질문 |
| 결과가 나온 뒤의 평범한 질문 | **상담 에이전트** — 도구를 돌려 답한다 |
| 계산 전에 결과를 물음 | 되묻지 않고 진행 상황을 말한다 |
| 붙여넣은 문자 | 사기 확인 (상담 중에도) |

**결과가 나온 뒤의 질문을 상담으로 넘기는 갈래**가 이 설계의 핵심이다. 이것이 없으면
대화를 마친 사용자가 무슨 말을 해도 아무 일도 일어나지 않는다.

목적지를 바꿨으면 그 사실을 응답에 담아 돌려준다. 분류는 'profiling' 인데 상담
답변이 나오면 화면의 표시와 실제가 어긋나고, trace 를 보여주는 화면에서 바로 눈에 띈다.

한 가지 겹침을 실제로 고쳤다. **"이 결과 믿어도 되나요?"의 '믿어도'가 사기 확인
표현과 그대로 겹친다.** 내 계산을 묻는 말이 남의 연락 확인으로 가면 엉뚱한 위험도
판정이 돌아온다. 남이 보낸 것을 가리키는 말(문자·카톡·연락)이 없을 때는 결과 질문으로
먼저 가르도록 순서를 바꿨다.

```bash
uvicorn web.api:app --host 0.0.0.0 --port 8000
```

`core/` 와 `agents/` 는 **한 줄도 고치지 않았다.** W1 에서 "core 는 LLM 도 UI 도
모른다"고 정한 것의 배당금이다. `web/api.py` 는 그것들을 HTTP 로 감싸는 얇은
어댑터일 뿐이고, Streamlit 앱도 그대로 남아 있다.

### 빌드 도구를 쓰지 않은 이유

프런트엔드는 순수 HTML/CSS/JS 다. React + 번들러를 얹으면 HPC 에 node 를 깔고
빌드 단계를 거쳐야 하는데, 그건 발표 당일 실패 지점이 하나 늘어나는 것이다.
차트도 외부 라이브러리 없이 SVG 로 직접 그린다. 오프라인에서도 열린다.

### 시니어 접근성

| 항목 | 구현 |
|---|---|
| 글씨 크기 | 기본 20px. 보통/크게/아주 크게 3단계 (기본값이 이미 커야 한다) |
| 고대비 | 흑백 + 테두리 강조 모드 |
| 음성 | 브라우저 내장 Web Speech API. 외부 서비스도 API 키도 불필요, 속도 0.95배 |
| 터치 영역 | 누르는 것은 최소 48px |
| 색 의존 배제 | 위험도를 색만으로 표시하지 않고 아이콘·글자를 함께 |
| 줄바꿈 | `word-break: keep-all` — 한국어가 낱말 중간에서 끊기지 않게 |
| 키보드 | 포커스 링 항상 표시, 본문 건너뛰기 링크, ARIA 탭·진행률 |

### 결과를 두고 이어서 묻기

에이전트를 만들어 놓고도 한동안 어떤 화면에서도 쓰지 않았다. `Advisor` 클래스로만
존재했고 사용자가 "생활비 50만원 줄이면요?"를 물어볼 입구가 없었다.

- **대화가 끝나도 입력창을 닫지 않는다.** 닫으면 상담 에이전트에 닿을 길이 없다
- 결과 화면으로 넘기는 것은 **처음 한 번만**. 질문마다 화면이 튀면 대화를 이어갈 수 없다
- 예시 질문 세 개를 눌러볼 수 있게 뒀다. 시니어 사용자에게는 "무엇이든 물어보세요"
  보다 이쪽이 낫다 — 빈 입력창 앞에서 멈추는 것이 가장 흔한 이탈이다
- 답변 아래에 **실행 기록**을 접어 둔다. 먼저 보여야 하는 것은 답이고, 근거는
  "눌러서 확인"이면 충분하다

### 알려진 제약

멀티 워커로 띄우면 메모리 캐시가 워커마다 갈린다. 세션 자체는 sqlite 에 있어
복원되지만, 같은 세션이 워커를 옮겨 다니면 매번 다시 읽는다. 실서비스로 가면
캐시를 Redis 로 옮기거나 sticky session 이 필요하다.
