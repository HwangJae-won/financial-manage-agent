# 은퇴 시니어를 위한 내 자산 AI 네비게이터

퇴직 전후 55~64세 중장년층을 대상으로, 자산·소득·연금을 종합 분석해
"그래서 지금 무엇을 해야 하는가"를 알려주는 금융 의사결정 지원 AI.

## 설계 원칙

> **`core/`는 LLM을 절대 호출하지 않는다.**
> LLM은 (a) 사용자 입력을 구조화하고 (b) 계산 결과를 설명하는 양 끝단에만 존재한다.

금융 서비스에서 숫자를 LLM이 만들면 환각 리스크를 통제할 수 없다.
모든 계산은 `core/`의 순수 파이썬 함수가 담당하고, LLM에는 "제시된 숫자만
인용하고 직접 계산하지 말 것"을 강제한다.

`schedule.py`가 분리되어 있는 이유: 퇴직월·연금개시월 안분과 물가연동처럼 틀리기
쉬운 규칙을 결정론적 엔진과 몬테카를로가 **공유**하게 해서 두 엔진이 조용히
어긋나는 것을 막는다. 일치 여부는 "변동성 0이면 몬테카를로가 결정론적 결과와
같아야 한다"는 테스트로 강제한다.

## 계산 규약 (발표 대응용)

1. 시뮬레이션은 **퇴직 시점부터** 시작한다. 퇴직 전 축적은 반영하지 않는다(보수적).
2. 투자수익은 **연초 잔액 기준**, 인출은 연말 발생으로 본다.
3. 생활비는 매년 물가상승률만큼 증가. 국민연금은 법정 물가연동 반영.
   기타소득(임대·근로)은 물가에 연동하지 않는다(보수적).
4. 세금은 이자·배당 성격 수익(현금성·채권)에만 부과. 국내주식 양도차익은
   소액주주 비과세 현실을 반영해 과세하지 않는다.
5. 퇴직 연도와 연금 개시 연도는 개월 단위로 안분한다.
6. **세금·건강보험료는 실효세율 근사다. 화면에 "참고용" 고지가 필수다.**
7. 국민연금을 법정 개시연령보다 미루면 연 7.2% 가산, 앞당기면 연 6% 감액하며
   양쪽 모두 최대 5년이다. 조정된 금액은 평생 유지된다.
8. 몬테카를로는 자산군 간 상관계수 0, 연도 간 독립, 정규분포를 가정한다.
   실제 시장의 상관과 두꺼운 꼬리를 반영하지 않으므로 꼬리 위험을 과소평가할 수 있다.

가정값의 근거는 전부 `data/assumptions.yaml`의 주석에 있다.

## 기획서에서 의도적으로 벗어난 지점

**리스크 스코어에 지속가능성 상한을 추가했다.** 기획서의 가중치는 단기 항목
(소득공백기 30% + 유동성 25%)에 55%가 몰려 있어, "지금은 현금이 넉넉하지만
69세에 파산이 확실한" 사람에게도 87점이 나온다. 화면에 *양호 87점*과
*만 69세 자산 고갈*이 나란히 뜨면 사용자는 무엇을 믿어야 할지 알 수 없고,
심사에서도 바로 지적받을 지점이다.

가중치 자체는 기획서를 그대로 두되, 시뮬레이션이 파산을 가리키면 종합 점수가
그 사실을 넘어설 수 없게 상한을 뒀다 (75세 이전 고갈 → 40점, 85세 이전 → 60점).
또 `장기소득` 항목은 연금/생활비 비율뿐 아니라 실제 고갈 시점을 함께 반영한다.

가중치를 바꾸는 편이 낫다고 판단되면 `core/risk_score.py`의 `WEIGHTS`와
`_sustainability_cap` 을 함께 조정할 것.

## 검증 기준

기획서 예시 인물(2026년 12월 퇴직, 금융자산 2.2억, 월 생활비 300만,
국민연금 월 150만·2030년 개시)에 대해 엔진이 산출하는 값:

- 소득공백기 **4년**
- 생활비 충당 가능 **6.2년** ← 기획서의 "약 6.2년"과 일치
- 연금 개시 시점 잔액 **1억 1,855만원**
- 금융자산 고갈 **2035년(만 69세)**
- 은퇴 재무 안정도 **40/100 (부족)** — 원점수 87점에 지속가능성 상한 적용

이 숫자들은 `tests/test_demo_regression.py`에 고정되어 있다.
가정값을 바꿔서 깨지면, 테스트를 고치지 말고 **바뀐 숫자가 의도한 것인지 먼저 확인**할 것.

|---|---|---|

## LLM 연결

`.env` 한 줄로 프로바이더를 바꾼다. 키가 없으면 자동으로 mock 이 되고,
설정이 잘못돼도 앱은 죽지 않고 mock 으로 떨어진다.

```
FINAGENT_LLM_PROVIDER=anthropic   # anthropic | openai | mock (비우면 자동)
ANTHROPIC_API_KEY=sk-ant-...
```

연결 확인: `python scripts/smoke_llm.py`

**구독은 API 사용권이 아니다.** Claude Max 도 ChatGPT Plus 도 API 결제는 별도다
(console.anthropic.com / platform.openai.com). OpenAI 는 모델 ID 라인업이 자주
바뀌므로 기본값을 두지 않았다 — `OPENAI_MODEL` 을 직접 지정해야 한다.

### LLM 이 숫자를 지어내지 못하게 하는 두 겹의 방어

1. **사전** — 프롬프트에 계산 결과를 사실 목록으로 넣고 그 안의 숫자만 쓰라고 지시
2. **사후** — 생성된 문장의 모든 숫자가 사실 목록에 있는지 기계적으로 검사
   (`agents/explain.py` 의 `verify_numbers`)

2번이 핵심이다. 프롬프트 지시는 지켜지지 않을 수 있지만 검사는 확실하다.
검증에 걸린 숫자는 화면에 경고로 표시된다. 기획서 ⑧ "AI 금융정보 신뢰 검증"을
가장 값싸고 확실하게 구현한 형태다.

## 금융사기 탐지 (기능 ⑦)

세 겹으로 본다:

1. **규칙** (`data/fraud_rules.yaml`) — 레드플래그 9종. LLM 없이 동작하고,
   **어떤 표현이 걸렸는지 그대로 보여준다.** 근거를 댈 수 없는 경고는
   시니어 사용자에게 무의미하다.
2. **정책 대조** (`data/policy_facts.yaml`) — "제도가 바뀌었으니 갈아타라"는 주장을
   공식 팩트시트와 맞춘다. **발표 / 입법예고 / 국회통과 / 공포 / 시행**을 구분하는
   것이 기획서의 핵심 차별점이다. 뉴스는 이걸 구분하지 않는다.
3. **프로필 연결** — "고객님은 ISA에 5,000만원을 보유하고 계십니다"처럼
   실제 자산과 엮는다. 보유하지 않은 상품을 근거로 든 권유는 그 자체가 신호다.

측정된 동작 (기획서 예시 사기 문자):

| | 결과 |
|---|---|
| 사기 문자 | 위험 · 신호 6개 검출 (원금보장+고수익, 비현실 수익률, 재촉, 비공식 채널, 제도 빙자, 비밀 유지) |
| 정상 은행 안내 | 낮음 · **오탐 0** ("연 3.2%"는 정상 범위로 통과) |

정밀도가 재현율만큼 중요하다. "맨날 위험하다고만 한다"고 느끼면 사용자는
경고를 무시하게 되고, 그때부터 이 기능은 없는 것과 같다.

⚠️ `data/policy_facts.yaml` 은 **예시 데이터**다. 발표 전에 원문으로 최신화할 것.

## 일회성 큰 지출

이 연령대의 계획을 실제로 무너뜨리는 것은 매달의 생활비가 아니라 **한 번에 나가는
큰돈**이다. 자녀 결혼자금, 목돈 의료비, 주택 수리. 매년 일정한 생활비만 가정하면
"그래서 결혼자금 5,000만원은 어디에 반영됐나요"라는 질문에 답할 수 없다.

기획서 예시 인물에게 2029년 자녀 결혼자금 5,000만원을 넣으면:

| | 고갈 시점 |
|---|---|
| 지출 없음 | 만 69세 |
| 결혼자금 5,000만원 | **만 66세** (3년 앞당겨짐) |

금액은 **퇴직 시점 기준**으로 본다. 월 생활비와 같은 규약이라 발생 연도까지
물가상승률만큼 커진다(보수적).

프로파일링 질문은 12개 그대로 두었다. 질문을 하나 늘리는 것보다 **에이전트가
대화로 다루는 편**이 이 기능에 맞다 — "내후년에 결혼자금 5천만원이 나가면요?"

## 처방 엔진 — "그래서 무엇을 하면 되나"

W7 까지의 엔진은 **진단만** 했다. "만 69세에 금융자산이 고갈됩니다"에서 멈춘다.
`core/prescribe.py` 는 같은 엔진을 **역방향으로** 써서 그다음을 답한다.

    "월 생활비를 187만원으로 줄이시면 만 95세까지 유지됩니다."

레버 세 개를 각각 역산한다. 기존 `simulate()` 위에 얹는 구조라 계산 규약과
회귀 테스트가 그대로 유지된다.

| 레버 | 탐색 방법 | 이유 |
|---|---|---|
| 월 생활비 | 이분 탐색 | 줄일수록 유리 — 단조 |
| 국민연금 개시 시기 | **전 구간 계산** | 단조가 아니다 (아래) |
| 기타 월소득 | 이분 탐색 | 늘릴수록 유리 — 단조 |

### 연금 레버에 이분 탐색을 쓰면 안 되는 이유

연기하면 수령액은 늘지만 그때까지 자산을 더 헐어야 한다. 어느 쪽이 유리한지는
사람마다 뒤집힌다. 기획서 예시 인물(DEMO)은 **연기가 오히려 불리하다**:

| 개시 연령 | 월 수령액 | 고갈 |
|---|---|---|
| 만 62세 (조기) | 132만원 | 만 70세 |
| 만 64세 (법정) | 150만원 | 만 69세 |
| 만 69세 (연기) | 204만원 | 만 67세 |

자산이 빠르게 줄어드는 사람에게는 "지금 들어오는 현금"이 더 중요하다.
그래서 가능한 연령을 전부 계산해 비교한다. 조기 수령을 권할 때는 **감액이 평생
유지된다**는 경고가 반드시 함께 나간다.

조기노령연금은 소득이 있는 동안 받을 수 없으므로 퇴직 이전 연령은 후보에서 제외한다.

### 측정된 동작

| 인물 | 결과 |
|---|---|
| DEMO (69세 고갈) | 생활비 **월 113만원↓(37.7%)** 또는 추가수입 **월 162만원** |
| DIVERSIFIED (고갈 없음) | 여유는 **월 5만원뿐** — 98점이라는 점수보다 빠듯하다 |

DIVERSIFIED 의 여유가 월 5만원이라는 것은 안정도 98점만 보고는 알 수 없는
사실이다. 처방 엔진이 없었으면 드러나지 않았을 값이다.

### 검증 방식

처방이 틀리면 진단이 틀린 것보다 나쁘다 — 사용자가 그 말을 믿고 생활을 바꾼다.
그래서 **왕복 검증**을 건다: 답한 값을 엔진에 다시 넣어 정말 목표까지 버티는지
확인하고, 한 칸(만원) 더 쓴 값은 실패하는지도 확인한다. 필요 이상으로 졸라매게
만드는 답도 틀린 답이다. 이분 탐색의 결과는 완전탐색 결과와 대조한다.

답은 항상 만원 단위다. "2,413,271원으로 줄이세요"는 사람이 쓸 수 없는 답이다.

### 하지 않는 것

조합 탐색(생활비도 줄이고 연금도 미루고)은 이 모듈에서 하지 않는다. 경우의 수가
곱으로 늘고, 무엇보다 **무엇을 포기할지는 사용자가 정할 문제**다. 레버별로 얼마가
필요한지만 정확히 답하고, 조합은 대화 에이전트에게 맡긴다.

## 민감도 분석 — 우리 숫자 자체를 흔들어 본다

이 서비스가 내놓는 모든 숫자는 가정 위에 있다. 심사·발표에서 "그 가정이 틀리면요?"는
반드시 나오는 질문이고, **답을 준비하는 것보다 화면에 미리 띄워두는 편**이 낫다.

남의 말을 "내 자산 기준 얼마"로 환산해 왔으니, 우리 출력도 같은 방식으로 환산한다.

### 측정된 동작

| 가정 | DEMO 흔들림 | DIVERSIFIED 흔들림 |
|---|---|---|
| 월 생활비 (±10%) | **4년** | **8년** |
| 물가상승률 (±0.7%p) | 1년 | 5년 |
| 투자 기대수익률 (±1.0%p) | 1년 | 4년 |
| 금융자산 평가액 (±10%) | 2년 | 4년 |
| 국민연금 수령액 (±10%) | 1년 | 3년 |

**두 인물 모두 월 생활비가 결과를 지배한다.** 사용자가 기억으로 답하는 값이라
오차가 크면서 지배력도 가장 크다 — "이 값을 정확히 아는 것이 가장 중요합니다"라고
말할 근거가 된다.

그리고 DIVERSIFIED 는 **안정도 98점 '양호'인데 생활비가 10% 늘면 만 87세에 고갈된다.**
점수만 보고는 알 수 없는 사실이고, 이 분석이 존재하는 이유다.

### 한계 (고지 필수)

한 번에 한 가지 가정만 흔든다(일변량). 가정들이 동시에 나빠지는 경우는 반영되지
않으므로 실제 최악은 이보다 나쁠 수 있다. 이 문장은 `caveat` 로 화면에 항상 나간다.
동시에 움직이는 상황은 몬테카를로가 다룬다.

### 구현 주의

`load_assumptions()` 는 `lru_cache` 로 전역 공유된다. 흔들어 보는 과정에서 원본을
건드리면 **이후 모든 계산이 조용히 틀어진다.** 반드시 `model_copy(deep=True)` 로
복사해서 바꾸며, 이를 테스트로 강제한다(`test_the_shared_assumptions_are_not_mutated`).

## 정책 영향 분석 (기능 ④·⑧, W7)

기획서의 정책 RAG(크롤링 + Vector DB + 시점 관리)는 문서 수집이 별도 프로젝트급이라
범위 밖이다. 대신 **ISA 세제 개편안 한 건만** 골라 계산 끝까지 연결했다.
뉴스 요약은 포털에도 있다. **"고객님 자산 기준으로 연 ○○원"** 이 나와야 이 기능이
존재할 이유가 생긴다.

### 어떻게 계산하나

팩트시트의 세제 파라미터를 캐시플로우 엔진에 주입해 **현행 제도와 개편안을 같은
기준으로** 각각 재시뮬레이션하고 차이만 본다. 세제 외의 규약(수익 시점, 물가연동,
퇴직월 안분)은 두 시뮬레이션이 공유하므로 결과 차이는 오직 세제 차이다.

`simulate(tax_model=...)` 이 그 자리다. 넘기지 않으면 기존 규약 그대로라
W1~W6 의 숫자는 한 개도 바뀌지 않는다 (`test_default_tax_model_changes_nothing`).

### 측정된 동작

| 인물 | 결과 |
|---|---|
| DEMO (ISA 없음) | **영향 없음** — "ISA 계좌를 보유하고 계시지 않습니다" |
| DIVERSIFIED (ISA 5,000만원) | 연 **2만 6,706원** · 은퇴 기간 전체 **26만원** 절감 |
| ISA 4억으로 늘려도 | 연 **9만 8,621원** — 상한에 막힌다 |

**결론이 "영향이 거의 없습니다"라는 점이 이 기능의 핵심이다.** 사기 문자는 늘
"제도가 바뀌니 지금 갈아타라"고 말한다. 실제 영향을 원 단위로 계산해 보여주는 것이
그 주장에 대한 가장 값싸고 확실한 반박이다.

### 구조적 상한 — 이 기능에서 가장 강한 문장

비과세 한도만 올리는 개편이라면 절감액은 **(한도 증가분 ÷ 의무가입기간) × 분리과세율**
을 넘을 수 없다. 보유액이 아무리 커도 그렇다. 지금 파라미터로는 **연 9만 9,000원**이다.

> "이 개편안으로 줄어드는 세금은 보유액이 아무리 크셔도 연 9만 9,000원을 넘지 않습니다."

개인의 자산을 몰라도 말할 수 있는 문장이고, 갈아타기 권유에 대한 답이 된다.
분리과세율까지 바뀌는 개편이면 상한이 없어지므로 `max_annual_saving` 은 `None` 이 된다.

### 신뢰 표시 (⑧)

모든 정책성 출력에 **출처 · 확정여부(5단계 중 몇 번째) · 시행일 · 확인일**이 붙는다.
시행되지 않은 건에는 "아직 확정되지 않았습니다" 문구가 강제된다 (`PolicyFact.notice`).

```
⚠️ 발표 (미확정) | ISA 세제 개편 논의
출처: 기획재정부 세법개정안 · 확정여부: 발표(1/5단계) · 시행일 미정 · 확인일: 2026-08-13
```

뱃지 문구는 서버가 완성해서 보낸다. 사기 확인 화면과 제도 변화 화면이 **같은 문자열**
을 쓰기 위해서다 — 같은 제도가 두 화면에서 다르게 표시되면 그 자체가 불신 요인이다.

### 알려진 한계

- ISA 가 전체 금융자산에서 차지하는 비중이 은퇴 기간 내내 유지된다고 본다.
  계좌 간 이동이나 만기 재가입은 반영하지 않는다.
- 기본 분석 화면의 세금은 ISA 비과세 혜택을 반영하지 않은 보수적 값이다.
  이 비교는 현행·개편안 **양쪽 모두에** ISA 세제를 적용해 차이만 본다.
- 계약기간 총액 한도를 의무가입기간으로 나눠 연 환산한다. 해마다 한도가 새로
  채워진다고 보면 실제보다 유리해지므로 이쪽이 보수적이다.

## Supervisor 라우팅

목적지가 둘 이상이 된 시점(사기 탐지 추가)에 만들었다. **규칙이 먼저, LLM 은
애매할 때만.** 붙여넣은 사기 메시지는 길고 광고성 표현이 있어 구조적으로
알아볼 수 있으므로 LLM 을 부를 이유가 없다 — 빠르고, 공짜고, 왜 그렇게
분류했는지 설명된다. 분류에 실패해도 기본 경로로 보내 대화가 끊기지 않는다.

## 웹 (W6)

```bash
uvicorn web.api:app --host 0.0.0.0 --port 8000
```

`core/` 와 `agents/` 는 **한 줄도 고치지 않았다.** W1 에서 "core 는 LLM 도 UI 도
모른다"고 정한 것의 배당금이다. `web/api.py` 는 그것들을 HTTP 로 감싸는 얇은
어댑터일 뿐이고, Streamlit 앱도 그대로 남아 있다.

### 빌드 도구를 쓰지 않은 이유

프런트엔드는 순수 HTML/CSS/JS 다. React + 번들러를 얹으면 HPC 에 node 를 깔고
빌드 단계를 거쳐야 하는데, 그건 발표 당일 실패 지점이 하나 늘어나는 것이다.
차트도 외부 라이브러리 없이 SVG 로 직접 그린다. 오프라인에서도 열린다.

### 시니어 접근성

| 항목 | 구현 |
|---|---|
| 글씨 크기 | 기본 20px. 보통/크게/아주 크게 3단계 (기본값이 이미 커야 한다) |
| 고대비 | 흑백 + 테두리 강조 모드 |
| 음성 | 브라우저 내장 Web Speech API. 외부 서비스도 API 키도 불필요, 속도 0.95배 |
| 터치 영역 | 누르는 것은 최소 48px |
| 색 의존 배제 | 위험도를 색만으로 표시하지 않고 아이콘·글자를 함께 |
| 줄바꿈 | `word-break: keep-all` — 한국어가 낱말 중간에서 끊기지 않게 |
| 키보드 | 포커스 링 항상 표시, 본문 건너뛰기 링크, ARIA 탭·진행률 |

### 알려진 제약

세션은 **메모리 딕셔너리**에 있다. 프로세스를 재시작하면 사라지고 여러 워커로
확장할 수 없다. 데모 범위에서는 충분하지만 실서비스로 가면 Redis/DB 로 옮겨야 한다.
